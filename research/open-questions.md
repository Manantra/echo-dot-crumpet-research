# Open questions

1. **Partly resolved:** official 2025 Crumpet OTAs supply full `brhgptpl_*` images with the **2023 build string `20231103_072325`**. Their image hashes differ from the community-device dump SHA-256 `d0d43eea2d5d52835007e375a3214fa4c6bf1a7c319e52ab442b7567e318992b`. Determine if this comes from formatting, per-device differences, or other content before claiming identity.
2. **Partly resolved:** entry-point mapping validated from the `FILE_INFO` load address and ARM branch of the stored images. Independently establish live relocation/runtime execution layout, particularly for the 2019 NAND excerpt.
3. **Partly resolved:** 2022-vs-2023-built memory-range checks and ATF/TEE load-then-verify ordering have been disassembled with direct call sites ([memory guard](../docs/arm-range-check-analysis.md), [TEE call graph](../docs/tee-load-signature-order.md)). Next: compare 2019 and inspect anti-rollback/DA-verification routines at validated addresses.
4. **Resolved (2026-10-08):** Official September 2021 OTA contains four `brhgptpl_*` preloader entries, all extracted and SHA-256 verified. See [results](../docs/ota-2021-analysis.md). Next: carefully map 2021 image addresses and compare functions against 2019.
5. Explain the BROM/MTKClient DA stage 2 failure without writing anything.
6. **Partly resolved (2026-10-09):** [Crumpet Amonet source/GPT audit](../docs/amonet-crumpet-unreachable-lk-and-expdb.md) confirms `LK_PART_NAME "expdb"` is **not in either CRC-verified 2019 or Nov-2025 NAND GPT** (18 named entries), and literal `expdb` is absent from the 2025 preloader bytes. Non-GPT `part_get` lookup/alias remains unverified; do not imply a functional partition exists.
7. **Partly resolved (2026-10-09):** [A public Crumpet TWRP source target exists](../docs/crumpet-twrp-emmc-vs-nand-audit.md) with a prebuilt ARM kernel, but shared recovery fstab/init use `emmc` and MMC path assumptions. Five fstab names are absent from verified early NAND GPT (though later virtual devices/aliases are possible). Neither a boot-tested Crumpet `recovery.img` nor a recoverable NAND implementation has been demonstrated.
8. **Partly resolved:** the updated guard's encoded BSS interval `[0x00102180,0x00109DAC)` contains the published payload's BDEV target `0x001086EC`; its `0x00108804` data extent would overlap protected BSS if the effective destination is zero. [Static source/bin check](../docs/sram-guard-exploit-intersection.md). **Partly resolved:** the TEE-header parser at `0x20F368`, state-driven address query `0x2160F4`, conditional calculator `0x216130`, guard at `0x20F490`, and subsequent bulk read are now corroborated by decoded Thumb calls in both 2023-era builds ([details](../docs/tee-header-address-processing.md)). **Still open:** determine the exact effective address for `0xFFFFFFFF` under all states and whether alternate parsing paths can skip the range checks; do not claim full mitigation without this proof.

9. **Partly resolved:** we verified LK binaries from official 2021–2025 OTAs and decoded the Fastboot `flash:` dispatcher, `unlock` validation at FILE+0x1F804 and separate `otucert`/`otucode` handlers at FILE+0x1F85E / +0x1F87C ([LK timeline](../docs/lk-image-timeline.md), [call graph](../docs/lk-fastboot-unlock-disassembly.md)). **Still open:** identify any independently documented legitimate Amazon signing-certificate issuance/authorization; do not infer that accepting command names permits unsigned unlock.
10. **Partly resolved:** source tracing shows the DA2 failure is an **exception or incomplete protocol reply** after transfer acknowledgement, not a diagnosed DRAM/NAND/security error. The two [distinct MT8167 DA2 binaries](../docs/da2-binary-emi-compatibility.md) have different drivers and BSS regions, but both fit within the **256 MiB `[0x40000000,0x50000000)`** measured in independent public Crumpet normal-boot logs. Four official preloader EMI trailers are byte-identical. [Our protocol/memory-map audit](../docs/da2-handoff-status-memory.md) identifies a 12-byte XFLASH status header and distinguishes returned error from missing USB response. **Still open:** determine whether Stage 2 executes any instructions on failing Crumpet hardware, classify its precise transport exception, and identify the selected DA filename/hash in existing logs. No blind hardware tests.
11. **New:** Establish a complete recovery plan for raw NAND including its four boot copies, ECC/BCH and PRBS scrambling; the [public MT8167 NAND utilities](https://github.com/gilderchuck/mtk-nand-utils) are a basis for offline reading but not proof of safe writeback.

12. **New:** Verify the impact of MTKClient's self-comparing `hw_sub_code` duplicate filter on multi-subcode loader metadata **offline**; the two observed MT8167 entries have matching subcode, so that particular bug is **not** an established Crumpet-specific cause. See [DA metadata audit](../docs/mtkclient-da-stage2-analysis.md).

13. **Non-destructive evidence only:** Use the [offline XFLASH response decoder](../scripts/decode_xflash_status.py) with an already captured, redacted 12-byte status header plus payload to distinguish successful reply, explicit error, bad framing and timeout. Need existing USB reconnect/transport logs, selected DA file hash and EMI hash; never infer a root method from an early DA1 sync.

14. **DA version/mode evidence:** A real Crumpet reports HW 0xCB00/SW1 but bundled DAs mark HW 0xCA00/SW0; source permits backward-compatible matching. A [separate same-revision MT8167 eMMC device](../docs/mt8167-hw-revision-da-selection.md) booted a V5-named DA in **Preloader** mode, while Crumpet reports fail via **BROM + EMI**. Next: compare existing traces for selected DA hash, mode, EMI handoff and USB response; do not infer a working unlock.

15. **DA1↔DA2 pairing and host setup-check bug (partly resolved):** The two bundled MT8167 DA1s contain the SHA-1 of *their respective* DA2 without the 0x100-byte signature trailer; cross-bundle references are absent. The upstream host [ignores False results from three DA1 setup calls](../docs/da1-da2-pairing-handoff-checks.md) even when it later reports a successful sync. Next: determine whether any existing Crumpet trace records these return values, effective patched/unpatched DA1/DA2 hashes and exact setup outcomes. This is not proof of a hardware exploit or a workaround; no DA mixing or testing on unrecoverable hardware.

16. **Latest OTA and boot-copy research:** [Latest catalogued Nov-2025 Crumpet OTA](../docs/latest-2025-ota-boot-payload-comparison.md) has the same SHA-256-verified LK as Jan-2024, and all sampled 2025 `brhgptpl_0` partitions have bit-identical MediaTek GFH image bytes from offset `0x8000` onward. Different whole-partition hashes come from differing NAND prefixes. The four Nov-2025 copies differ only by four copy-dependent fields at `0x100D`, `0x1011`, `0x101D`, `0x1021`. **Open:** reverse-map those prefix fields without assuming they are writable; test older truly different core generations separately. No firmware changing on hardware.
17. **Cross-chip Stage-2 failure:** [MTKClient issue #26](https://github.com/bkerler/mtkclient/issues/26) reports the *same* BROM/Kamakiri + patched DA + accepted EMI + Stage-2 timeout on MT6739; maintainer suspected unsuitable Preloader EMI, but trying several preloader versions did not settle it. Therefore do not treat the message as Crumpet-specific security proof; existing USB logs remain necessary.

18. **Major logical-layout question resolved:** the [public 2019 Crumpet excerpt and official 2021–2025 OTA images](../docs/crumpet-nand-gpt-2019-2025.md) contain CRC-valid GPT headers and 32-entry arrays (18 used), with **exactly the same 18 logical partition LBA ranges**. The four `BRLYT` copy fields equal their corresponding GPT first-LBA +0x8/+0x108. May→Nov-2025 header changes consist **only** of disk/unique-partition GUIDs and GPT CRC32 bytes (309 total). The 2019 excerpt uses different container offsets. **Still open:** physical NAND scrambling, ECC/OOB, bad blocks, per-device partitions and independently verified restore. A CRC-valid embedded GPT is **not** a writable PC GPT layout; do not flash or repair with generic GPT tools.

19. **Crumpet Amonet patch address safety blocker:** Five published constants from upstream `devices/crumpet.c` are direct RAM-write targets and **cannot be identified as the claimed function entries** in the stored-file mappings of five verified 2019–2025 Preloaders. The earliest `0x217F2C` hits an embedded USB diagnostic string in the 2019 dump. [Full offline patch-site report](../docs/amonet-hardcoded-patch-address-audit.md). **Still unknown:** which binary/version or relocated live RAM image the port targets, and whether its function patches are correctly grounded. Do not write the published constants or flash experimental TEE/NAND images.

20. **ARM bootstrap and RAM-location nuance (2026-10-09):** [Opcode-level startup disassembly](../docs/crumpet-arm-bootstrap-memory-map.md) across 2019, 2021, 2022 and 2025 confirms the literal BSS zero-fill range and the indirect ARM→Thumb handoff, and makes the stored-file address mapping less speculative. The 2019 and 2021 continuation *addresses* are equal but their Thumb bytes differ. Still **no live RAM snapshot**, and startup code cannot prove what regions contain at payload patch time. Next: independently establish live relocation and claimed function entries; no write experiments.

21. **Crumpet Amonet flow blocker (verified from original C source):** The port forces `usbdl_detect_key()` to true; because the device lacks `USB_CABLE_IN_ADDR`, `usb_cable_in()` also returns true. `main()` calls `enter_usbdl(0)` **before** the custom LK loader, so the source path enters a nonreturning `while(1)` handshake and never reaches `bldr_load_part("expdb",...)`. [Complete report](../docs/amonet-crumpet-unreachable-lk-and-expdb.md) and [offline checker](../scripts/audit_amonet_crumpet_boot_flow.py). Need a *verified* working downstream port, not a speculation-based modification to this one. No live hardware execution demonstrated.

22. **Amonet Crumpet pointer integrity (2026-10-09):** The [pinned port `PART_GET_ADDR=0x20F250`](../docs/crumpet-amonet-part-get-thumb2-misalignment.md) lands *inside the trailing halfword of a 32-bit Thumb instruction* in official 2022 and Nov-2025 Preloaders. 2021 resolves at an instruction boundary but remains within another routine. The [offline source-and-firmware checker](../scripts/audit_crumpet_amonet_part_get_entry.py) requires exact known firmware SHA-256 and code anchor. Remaining: exact runtime relocation and function entry mapping; do not try function pointers on the device.
23. **Crumpet TWRP device tree vs raw NAND:** The [August-2026 TWRP source tree](../docs/crumpet-twrp-emmc-vs-nand-audit.md) inherits shared `emmc` storage paths, and five expected fstab labels are not in the early GPT. Need real read-only kernel enumerated block devices/mount paths and independent proof the recovery boots; no working TWRP or safe NAND writeback established.

24. **2019 donor-era code validated against original archival bytes (2026-10-09):** The [latest root viability report](../docs/crumpet-root-unlock-feasibility-2026-10-09.md) proves fixed `PART_GET_ADDR` is *also* the second halfword of a 32-bit instruction in public 2019 Crumpet (`ldr.w` at 0x20F24E); fixed `TEE_SET_ENTRY_ADDR` and `MTEE_VERIFY_DECRYPT_ADDR` land inside ASCII strings. Thus the publicly downloadable 2019 archive does not validate the upstream port's pointer constants. Unknown alternate donor/live memory relocations remain open. [Pinned read-only pointer verifier](../scripts/audit_2019_amonet_string_pointer_collisions.py).
25. **Signed old-firmware rollback eligibility unproven:** We find five identical MediaTek GFH security records (BL_INFO/BROM_CFG/ANTI_CLONE/BROM_SEC_CFG/BL_SEC_KEY) across public 2019 and official 2021/2025 Preloader images, numeric signature type=3, signature length=292. This does **not** verify old signature acceptance, hardware antirollback policy, correct per-unit configuration or a safe flash route. [Source/hash-validated GFH report](../docs/crumpet-root-unlock-feasibility-2026-10-09.md).
26. **Raw NAND recovery geometry defined but method open:** 2019 UART identifies Macronix MX30LF4G28AD, 131072 pages of 4096 main +256 OOB, BBT at two final block starts on that unit. [Offline file size checker](../scripts/check_crumpet_raw_nand_dump_size.py) refuses to certify ECC/bad blocks. Still need exact modern chip ID, two readback-matching main+OOB dumps, scrambling and usable independent recovery. Without this, no safe boot-copy downgrade.

27. **DA2 NAND-chip absence disproven for pinned V5 build:** [Latest static direct DA2 table audit](../docs/mtkclient-stage2-nand-profile-transport.md) verifies stock `MTK_DA_V5.bin` contains a pointer from a NAND profile to exact string `MX30LF4G28AD`, exact Crumpet-reported 6-byte ID and correct 4096+256 page/OOB fields. Therefore lack of historical NAND-ID support is not an adequate explanation for failure **before** `get_nand_info`. No DA2 execution proven; current boards may have different chip IDs.
28. **MTKClient Stage-2 USB diagnostics (2026-10-09):** [Offline AST/packet audit](../scripts/audit_xflash_stage2_transport.py) confirms a short 12-byte status header raises a Python exception classified as `Stage was't executed. Maybe dram issue ?.`; Stage-2 `timeout=0.5` controls only sleep, status USB backend defaults to 100 retries, USB reconnection is deferred until `boot_to` succeeds, and `send_data` can spin on persistent unsuccessful writes. **Unresolved:** whether any real Crumpet DA2 USB disconnect/re-enumeration, DRAM failure, signature error, DA1 setup error or DA2 startup loop occurs. Needs existing owner-authorized redacted USB timings or other safe observational evidence, not speculative flashing.

29. **DA1→DA2 real runtime parameter handoff (2026-10-09):** [Both stock DAs disassembled](../docs/mt8167-da2-bootstrap-r0-magic-sync.md). ARM DA2 prologue stores incoming `R0` at `0x40000020`; Thumb `kmain` copies 88 (V5) or 64 (alternative) bytes into BSS before scheduling `bootstrap2`; both require first-word magic `0xFE4A4D42`. A mismatch branches to a literal endless loop before USB ready `SYNC`; DA1 binaries contain the exact magic. Both DA2 editions *correctly* build 12-byte XFLASH header plus 4-byte SYNC via known IO function pointers. **Still unknown:** is the live Crumpet `R0` pointer valid and the structure populated with the right DA1 pairing, or is the stall later in platform init/USB? Existing redacted UART/USB trace could discriminate; no invasive tests.

30. **BROM EMI auto-search and 2019 archived Preloader false parsing:** [Read-only original MTKClient parser and firmware audit](../docs/crumpet-emi-2019-layout-and-brom-nand-gap.md) proves the XFLASH BROM missing-EMI auto-search uses eMMC/UFS info and eMMC CID, not raw-NAND ID, potentially proceeding without usable DRAM setup. The **same 400B EMI v28** is embedded in SHA-verified public 2019, official 2021 and Nov-2025 Preloaders; **2019 GFH-trimmed last word `0xffffffff`** makes actual `m_extract_emi()` return an **incorrect 37152B** while still claiming version 28. New [pinned offline hash/length parser](../scripts/audit_crumpet_emi_fallback.py) reproduces this. Next: determine whether public Crumpet Stage2 debug reports included explicitly provided, correct EMI and actual `DRAM setup passed` status; this research does not authorize DA uploads, flashing or cross-version downgrade.

31. **DA1→DA2 pairing more strongly validated (2026-10-10):** [Full original DA1 construction trace](../docs/mt8167-da1-runtime-parameter-block-handoff.md) proves both matched DA1 versions write `0xFE4A4D42` to first word of RAM param buffer, copy 24+56B V5 or 24+32B alternate after an 8B header, then put buffer address in `R0` for a callback-targeted `BLX`. The respective DA2 routines copy exactly 88/64B and test precisely this magic. **A static mismatch in a correct, intact pair is no longer a primary hypothesis**. Still unknown: actual runtime data in source SRAM, validity of earlier stack-derived indirect entry address, EMI/DRAM initialization and USB state. A live trace would be necessary; no speculative uploads or NAND writes.

32. **Host status semantics now more discriminating (2026-10-10):** [Pinned stock DA1 checksum and host acknowledgement analysis](../docs/da1-sha1-status-vs-da2-sync-ack.md) confirms each stock DA1 20-byte SHA-1 of own original DA2, opcode compares and emits `0xC0070004` on mismatch. MTKClient's `send_data` only returns True for first status==0, and `boot_to` prints `Upload data was accepted...` **only after that positive first ACK**. DA2 framed `SYNC` requires a **separate second status**. Existing public Crumpet timeout logs should not be called *reported DA1 hash rejects*. Still unknown: actual patched on-device SHA/bypass path, R0 content, DRAM quality and physical USB event sequence. Need redacted same-device trace, not blind flashing.

33. **Runtime-mutated DA1→DA2 data block identified (2026-10-11):** [New exact original Thumb source-table audit](../docs/crumpet-da1-mutable-state-and-october-2026-unlock-status.md): second copied source V5 at `0x2393B8` (56B) is directly referenced by 16 literal addresses and has 6 verified original state-field writes; alternative at `0x222C50` (32B) has 10 occurrences and 4 writes. The first 24B source in each original appears as a single literal occurrence at the transfer site. No live contents verified; need distinguish DA1 setup/EMI vs dynamic state vs DA2 USB acknowledgment from an already captured Crumpet trace, not assumptions.
